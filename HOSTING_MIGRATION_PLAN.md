# GitHub Pages -> Free CDN Host Migration Plan

**Context:** `tradersgag6.github.io/esrealty` exceeded the free GitHub Pages Cached Egress quota
(grace ends 2026-10-04; then requests return 402). The published site is tiny (~3 MB) — the quota
hit is traffic-driven, not size-driven. Migrating to a free CDN host fixes the egress ceiling.

**Recommendation:** **Cloudflare Pages** (free: ~unmetered static bandwidth on standard infra,
much larger free allowance than GitHub Pages; no custom-domain charge). Netlify (100 GB/mo free) is
the alternative.

---

## 1. Understand what you're migrating

The site is a **static SPA plus a backend-provided edge function**:

| Piece | Where it lives | Migration impact |
|-------|----------------|------------------|
| Static site (html/css/js, images) | Git repo root (Pages branch = `master`/`main`) | Move repo root as build output |
| Backend / data | **Supabase** (`mrngaqtbaseewzcsogqi.supabase.co`), publishable key in `js/*` | **None** — domain-agnostic, keep as-is |
| Market-scan micro-backend | `market-scan/vercel` (Vercel config) | Separate; redeploy on Vercel (or Cloudflare Workers) — not part of this site host |

Cloudflare Pages builds from your git repo (same as Pages), so the repo structure stays.

---

## 2. Before migrating — decide the domain

| Option | Free | Impact |
|--------|------|--------|
| **Keep `*.pages.dev` / `*.netlify.app` subdomain** | Yes | No domain work; but you lose the `tradersgag6.github.io` vanity |
| **Bring your own domain** (e.g. `esrealty.example.com`) | Yes via Cloudflare | Better branding & stability; must set DNS + update URLs |

Recommended: bring the domain through **Cloudflare** (gives you the CDN + DNS in one place).

---

## 3. Pre-migration audit notes (cost-control, applies on the new host too)

- `js/app.js` is **1.09 MB** and `css/bootstrap.min.css` is **227 KB**. If you want lower per-load
  egress on the new host, code-split `app.js` and/or drop unused Bootstrap. Optional.
- `favicon.svg?v=2` uses a cache-busting query string → forces a re-fetch each load. Remove the
  `?v=2` after the move and rely on content-hash filenames / cache headers.

---

## 4. Migration steps (Cloudflare Pages)

### A. Spin up the project
1. Cloudflare Dashboard -> **Workers & Pages** -> **Create application** -> **Pages** -> **Connect to Git**.
2. Select the `esrealty` repo, branch `master` (or `main`).
3. **Build command:** `none` / `npm run build` if you add one.  **Output directory:** leave blank
   (repo root is the output — it already contains `index.html`, `.nojekyll`, `sw.js`).
4. Deploy. You'll get `https://<project>.pages.dev`.

### B. Serve-requirements
- **`.nojekyll`** is already present (needed because Pages would otherwise treat folders specially).
  Not required on Cloudflare but harmless.
- Add **404 handling**: Cloudflare serves `404.html` automatically if present (it already is).
- **SPA routing**: if the app uses hash routing only (`#/home`, `#/search`), nothing more is needed.
  If it depends on clean paths, add a Pages **`_redirects`** file:
  ```
  /*    /index.html   200
  ```

### C. Service worker scope (IMPORTANT)
- GitHub Pages served the PWA from `/esrealty/`, so `sw.js` registered with scope `/esrealty/`.
  On `*.pages.dev` (or your domain root) the scope becomes `/`, **caches must be versioned & purged**
  once, or old `esrealty-*` caches linger. The SW already deletes stale caches on `activate`
  (keeps only `esrealty-v4`, `esrealty-vendor-v4`, `esrealty-img-v1`). Bump `VERSION` to a new id
  (e.g. `esrealty-pages-v1`) so all clients get a fresh cache. Update your users by opening the site
  after deploy (navigate away from Pages).

### D. Domain + SEO + verification rewrites (if you bring a custom domain)
Update anywhere the hostname is hard-coded:
1. `sw.js` — the `VERSION` constant (see C).
2. `robots.txt` — `Sitemap:` already points at Supabase (host-agnostic). If you change domain, the
   `Sitemap`/canonical URLs in `supabase/functions/**/seo` regenerate from the new host.
3. Canonical/sitemap URLs generated by the Supabase `seo` edge function — update its base URL env/var
   to the new host (e.g. `https://esrealty.example.com`).
4. `google25a49039450dd2e9.html` — the Search Console verification file is tied to your *current*
   host. Keep it for the old host; re-verify the new domain in Search Console (it will furnish a new
   file) **only if you change domains**.
5. `manifest.webmanifest` — `start_url`/`scope` should point at the new origin/root, not `/esrealty/`.

### E. DNS (custom domain via Cloudflare)
1. In Pages, add your custom domain.
2. In Cloudflare DNS, point it to the Pages project (Pages auto-creates a `CNAME`/proxied record).
3. Wait for the free auto-HTTPS cert to issue.

---

## 5. Cutover & verify
1. Deploy to the new host, load the site on a desktop + iPhone SE/XR to re-verify the header fixes
   are present (fresh deploy = confirms whether those fixes were actually live before).
2. Confirm Supabase calls work (network is fine — backend is domain-agnostic).
3. Keep GitHub Pages alive through the grace period as a fallback; once the new host is stable,
   you can leave Pages as-is or take it down.

---

## 6. Netlify alternative (same steps, different UI)
- **Build command:** `none`, **Publish directory:** blank (repo root).
- Free tier: **100 GB/mo** egress — comfortably larger than GitHub Pages.
- Netlify handles HTTPS automatically; same `_redirects`/`.nojekyll` considerations.

---

## 7. Recommended immediate action (free, 15 min)
Even **before** migrating, this cut lives costs now:
1. Remove `?v=2` from the favicon include in `index.html` (stop forcing re-fetch each visit).
2. (Optional) trim `app.js`/`bootstrap` later.

But the durable fix for the egress *ceiling* is the migration above — GitHub Pages does not let you
raise the free cached-egress cap.
